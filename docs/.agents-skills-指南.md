# `.agents/skills` 使用指南

> 本文档汇总了 `.agents/skills/` 目录下全部 17 个 skill 的功能、使用场景及工作流路径。
> 这些 skills 为 [Matt Pocock 风格](https://www.aihero.dev/) 的工程工作流，特点是**高度结构化**、**状态驱动**、**可跨 session 延续**。

---

## 快速总览

| Skill | 一句话说明 | 触发词 |
|---|---|---|
| `/ask-matt` | 不知道用哪个 skill？先问它 | 不确定用哪个时 |
| `/setup-matt-pocock-skills` | 首次配置项目（issue tracker、标签、文档布局） | 第一次使用前 |
| `/grill-with-docs` | 有代码库时的需求追问（同时生成文档） | 有想法要讨论 |
| `/grill-me` | 无代码库时的需求追问 | 无代码库时 |
| `/grilling` | 核心追问引擎（逐层深入设计树） | "拷问我" |
| `/prototype` | 快速原型验证（用完即扔） | 需要跑起来验证 |
| `/handoff` | 会话交接（生成交接文档） | session 快满时 |
| `/to-prd` | 把讨论成果合成 PRD | 讨论结束，要出文档 |
| `/to-issues` | 把 PRD 拆成垂直切片任务 | 要开始开发了 |
| `/improve-codebase-architecture` | 架构体检（生成 HTML 报告） | 有空时跑一跑 |
| `/codebase-design` | 共享的模块设计词汇表 | 设计接口时 |
| `/domain-modeling` | 维护和打磨领域词汇表 | 术语定义不清 |
| `/triage` | 工单分拣（issue/PR 状态机） | 有 bug/PR 要处理 |
| `/tdd` | 测试驱动开发（red-green-refactor） | "TDD" / "测试" |
| `/diagnosing-bugs` | 硬核调试（6 阶段诊断） | "debug" / "排查" |
| `/teach` | 教学工作区（多 session 学习） | 想学新东西 |
| `/writing-great-skills` | 写 skill 的参考手册 | 写 skill 时 |

## 核心工作流：从想法到交付

```
/setup-matt-pocock-skills（仅需一次）
         │
         ▼
/grill-with-docs ──▶ /prototype（需要验证时）
         │                │
         │                ▼
         │           /handoff（session 满了交接）
         │                │
         │                ▼
         │           回到 /grill-with-docs
         │
         ▼
    /to-prd（生成 PRD）
         │
         ▼
    /to-issues（拆任务）
         │
         ▼
    逐个 issue 开发（可配合 /tdd）
```

### 关键原则

- **一条主流程**：grill → prototype（可选）→ PRD → issues → implement
- **Context 卫生**：步骤 1-3 尽量在一个 session 内完成，不要 compact/clear 直到 `/to-issues` 之后
- **跨 session 用 `/handoff`**：fork 到新 session，不是 compact 后继续

## Skill 详解

### 1. `/setup-matt-pocock-skills`

**功能**：配置项目以支持其他 engineering skills。只需运行一次。

**会创建的文件**：
- `docs/agents/issue-tracker.md` — issue tracker 配置（GitHub/GitLab/本地）
- `docs/agents/triage-labels.md` — triage 标签映射
- `docs/agents/domain.md` — 领域文档布局说明
- 在 `CLAUDE.md` 或 `AGENTS.md` 中插入 `## Agent skills` 区块

**决策点**：
- Issue tracker：GitHub / GitLab / 本地 markdown / 其他
- 是否把外部 PR 也作为 triage 表面
- Triage 标签词汇（默认等于角色名）
- 单上下文（`CONTEXT.md` + `docs/adr/`）还是多上下文（`CONTEXT-MAP.md`）

---

### 2. `/grill-with-docs`

**功能**：有代码库时的需求追问，同时创建领域文档。

**会创建的文件**：
- `CONTEXT.md` — 领域词汇表（纯术语，不含实现细节）
- `docs/adr/*.md` — 架构决策记录（难以逆转、令人惊讶、有真实权衡时）

**特点**：
- 有状态：每次追问的结果保留在文件中
- 使用 `/domain-modeling` 维护术语
- 一次只问一个问题

---

### 3. `/grill-me`

**功能**：无代码库时的需求追问。

**特点**：
- 无状态：不保存任何文件
- 与 `/grill-with-docs` 内容相同，只是不落地文档
- 适用于讨论不在任何 repo 中的想法

---

### 4. `/grilling`

**功能**：核心追问引擎。

**工作方式**：
- 逐层深入设计树的每个分支
- 一次只问一个问题，等待回答后再继续
- 对每棵树的分支提供推荐答案
- 如果问题可以通过探索代码库回答，优先探索代码库

**防止的问题**：
- 一次问太多问题导致用户困惑
- 跳过关键依赖关系

---

### 5. `/prototype`

**功能**：用"用完即扔"的代码回答一个具体问题。

**两个分支**：

| 问题类型 | 产出 |
|---|---|
| "逻辑/状态模型对吗？" | 终端交互式应用，推状态机 |
| "UI 长什么样？" | 多个 UI 变体，URL 参数切换 |

**规则**：
- 明确标记为 PROTOTYPE
- 一条命令即可运行
- 默认不持久化（状态在内存）
- 不写测试、不做错误处理、不搞抽象
- 每个操作后展示完整状态
- 用完即删，或把验证过的决策吸收进正式代码

---

### 6. `/handoff`

**功能**：把当前对话压缩成交接文档，让新 session 继续。

**保存位置**：系统临时目录（`$TMPDIR` 或 `/tmp`）

**包含内容**：
- 当前会话的精炼摘要
- 建议下一步使用的 skills
- 已存在的 artifact（PRD/ADR/issue）只引用路径，不重复内容
- 敏感信息脱敏

**与 `/compact` 的区别**：
- `/handoff` = fork：新 session，保留原对话 verbatim
- `/compact` = continue：同一对话，早期轮次被摘要

---

### 7. `/to-prd`

**功能**：基于已有对话直接合成 PRD，**不再追问**。

**PRD 模板结构**：
1. Problem Statement（用户视角的问题）
2. Solution（用户视角的解决方案）
3. User Stories（大量、编号、As a...I want...so that...）
4. Implementation Decisions（模块、接口、架构、schema、API）
5. Testing Decisions（测试策略、模块、先例）
6. Out of Scope
7. Further Notes

**注意事项**：
- 不包具体文件路径或代码片段（会过时）
- 例外：prototype 产出的精确决策片段可内联
- 自动发布到 issue tracker，标记 `ready-for-agent`

---

### 8. `/to-issues`

**功能**：把 PRD 拆成独立可抓取的垂直切片。

**垂直切片规则**：
- 每个切片贯穿**所有层**（schema → API → UI → tests）
- 不是水平切片（不要"先写所有 API，再写所有 UI"）
- 完成的切片可独立 demo/验证
- 先做完前置重构

**Issue 模板**：
- Parent（父 issue 引用）
- What to build（端到端行为描述，非分层实现）
- Acceptance criteria（可检查清单）
- Blocked by（依赖关系）

---

### 9. `/improve-codebase-architecture`

**功能**：扫描代码库，找出架构"深化"机会。

**产出**：自包含 HTML 报告（Tailwind + Mermaid）

**每个候选改进卡片**：
- Files（涉及文件）
- Problem（当前架构的摩擦点）
- Solution（改进方案）
- Benefits（locality、leverage、测试改善）
- Before/After 可视化图
- Recommendation strength（Strong / Worth exploring / Speculative）

**使用的词汇表**（来自 `/codebase-design`）：
- Module、Interface、Depth、Seam、Adapter、Leverage、Locality
- 删除测试、"接口即测试面"、"一个 adapter = 假设 seam，两个 = 真实 seam"

---

### 10. `/codebase-design`

**功能**：共享的模块设计词汇表和原则。

**核心概念**：

| 术语 | 定义 |
|---|---|
| **Module** | 有接口和实现的任何东西（函数、类、包），不用 "component/service" |
| **Interface** | 调用方必须知道的一切（签名、不变量、顺序约束、错误模式、配置、性能） |
| **Depth** | 接口背后的行为量 vs 接口复杂度。小接口大实现 = deep |
| **Seam** | 不改变此处代码就能改变行为的位置（Michael Feathers） |
| **Adapter** | 在 seam 处满足接口的具体实现 |
| **Leverage** | 调用方从 depth 获得的：学一点接口就能做很多事 |
| **Locality** | 维护者从 depth 获得的：改动集中在一点 |

**设计原则**：
1. **删除测试**：删掉模块，复杂度是消失还是转移到 N 个调用方？
2. **接口即测试面**：调用方和测试走同一个 seam
3. **一个 adapter = 假设 seam，两个 = 真实 seam**：不要过早抽象

### 11. `/domain-modeling`

**功能**：维护和打磨领域词汇表。

**文件结构**：
```
/
├── CONTEXT.md              # 领域词汇表（纯术语，无实现细节）
├── docs/adr/               # 架构决策记录
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── CONTEXT-MAP.md          # 多上下文时存在，指向各 CONTEXT.md
```

**工作方式**：
- 挑战用户与 `CONTEXT.md` 冲突的用语
- 把模糊用语磨尖成精确术语
- 用具体场景 stress-test 领域关系
- 检查代码是否与领域定义矛盾
- **实时更新**：术语确定后立即写入 `CONTEXT.md`

**ADR 创建条件**（必须同时满足）：
1. 难以逆转
2. 没有上下文会让人惊讶
3. 是真实权衡的结果

---

### 12. `/triage`

**功能**：把 issue/PR 推过 triage 状态机。

**角色（Category）**：
- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

**状态（State）**：
- `needs-triage` — 待评估
- `needs-info` — 等待报告者补充信息
- `ready-for-agent` — 足够明确，AFK agent 可直接抓取
- `ready-for-human` — 需要人类实现
- `wontfix` — 不处理

**流程**：
1. 收集上下文（issue/PR 正文、评论、标签、diff）
2. 推荐分类和状态（等用户确认）
3. **验证**：复现 bug / 确认 PR diff 确实做了声称的事
4. **追问**（如需要）：用 `/grilling` + `/domain-modeling`
5. 应用结果：贴 agent brief / 关 issue / 转状态

**注意**：
- `/triage` 只处理**外部 incoming** 的 issue/PR
- `/to-issues` 产出的 issue 已经是 agent-ready，不需要 triage

---

### 13. `/tdd`

**功能**：测试驱动开发。

**核心原则**：
- 测试验证**行为**（通过公共接口），而非实现细节
- 好测试 = 集成风格，读起来像规格说明
- 坏测试 = 绑定实现（mock 内部协作对象、测私有方法）

**反模式：水平切片** ❌
```
RED:   写 test1, test2, test3, test4, test5
GREEN: 写 impl1, impl2, impl3, impl4, impl5
```

**正确：垂直切片** ✅
```
RED→GREEN: test1 → impl1
RED→GREEN: test2 → impl2
RED→GREEN: test3 → impl3
...
```

**每个循环检查清单**：
- [ ] 测试描述行为，不是实现
- [ ] 测试只使用公共接口
- [ ] 测试能撑过内部重构
- [ ] 代码是当前测试的最小实现
- [ ] 没有 speculative features

### 14. `/diagnosing-bugs`

**功能**：硬核调试，6 阶段诊断流程。

| 阶段 | 目标 | 关键原则 |
|---|---|---|
| **1. 构建反馈循环** | 有可复现的 red/green 信号 | **这是整个 skill 的核心**。没有 loop 就不要继续。尝试：测试、curl、CLI、headless browser、重放 trace、最小子集、property/fuzz、git bisect、diff 循环 |
| **2. 复现 + 最小化** | 缩小到最小 still-red 场景 | 每个元素都是 load-bearing |
| **3. 生成假设** | 3-5 个可证伪的排序假设 | "如果 X 是原因，那么改 Y 会让 bug 消失" |
| **4. 仪器化** | 一次只改变一个变量 | 优先 debugger/REPL，其次 targeted log，绝不"log everything" |
| **5. 修复 + 回归测试** | 先写测试再修 | 如果没有合适的 seam，这本身就是发现 |
| **6. 清理 + 复盘** | 删除 `[DEBUG-...]` 日志 | 问"什么能预防这个 bug？" |

**最重要的原则**：
- 没有 red-capable 的命令，不要进入 Phase 2
- 不要在没有 loop 的情况下直接读代码猜原因

### 15. `/teach`

**功能**：创建教学工作区，支持多 session 学习。

**工作区结构**：
```
./
├── MISSION.md              # 学习动机
├── RESOURCES.md            # 资源列表
├── NOTES.md                # 用户偏好/工作笔记
├── ./lessons/*.html        # 课程（精美排版，每次一课）
├── ./reference/*.html      # 参考文档（速查/备忘）
├── ./learning-records/*.md # 学习记录（类似 ADR）
└── ./assets/*              # 可复用组件（样式、quiz widget 等）
```

**教学哲学**：
- 知识（Knowledge）：从高质量资源获取
- 技能（Skill）：通过交互式课程和反馈循环获得
- 智慧（Wisdom）：在真实社区中测试

**学习设计原则**：
- 每节课短小、可快速完成、给一个具体胜利
- 难度要落在"最近发展区"（Zone of Proximal Development）
- 区分 Fluency strength（即时检索）和 Storage strength（长期记忆）
- 使用 desirable difficulty：retrieval practice、spacing、interleaving

### 16. `/ask-matt`

**功能**：所有 user-invoked skills 的"路由器"。

**主流程（idea → ship）**：
1. `/grill-with-docs` — 梳理需求（有代码库）
2. 分支：需要 runnable 答案？→ `/prototype`
3. 分支：多 session 构建？→ `/to-prd` → `/to-issues`
4. 否则直接实现

**入口（On-ramps）**：
- Bug/请求堆积 → `/triage`

**代码库健康**：
- 有空时跑 `/improve-codebase-architecture`

**独立（Standalone）**：
- 无代码库讨论 → `/grill-me`
- 学习 → `/teach`
- 写 skill → `/writing-great-skills`

---

### 17. `/writing-great-skills`

**功能**：如何写出好的 skill 的参考手册。

**核心原则**：
- **可预测性**（Predictability）是 root virtue：每次走同样的流程，不是每次产出同样结果
- **信息层级**：in-skill step（有序动作）→ in-skill reference（按需查阅）→ external reference（通过 context pointer 加载）
- **何时拆分**：
  - 按 invocation：独立的 leading word 触发
  - 按 sequence：防止 premature completion
- **剪枝**：单一数据源、检查相关性、句子级 no-op 检测
- **Leading words**：用模型预训练中的紧凑概念锚定行为（如 _red_、_tight_、_tracer bullets_）

**失败模式**：
- **Premature completion** — 步骤没做完就想跳到下一步
- **Duplication** — 同一意思多处出现
- **Sediment** — 只加不减的过时层
- **Sprawl** — skill 太长，即使每行都有用
- **No-op** — 模型默认就会做的行为，写了等于白写

## 文件状态系统

这些 skills 共享一个文件状态系统：

| 文件 | 用途 | 由谁维护 |
|---|---|---|
| `CONTEXT.md` | 领域词汇表（纯术语，无实现细节） | `/domain-modeling` |
| `docs/adr/*.md` | 架构决策记录 | `/domain-modeling` |
| `docs/agents/*.md` | skill 配置（issue tracker、标签、布局） | `/setup-matt-pocock-skills` |
| `.out-of-scope/*.md` | 被拒绝的功能请求知识库 | `/triage` |
| `./lessons/*.html` | 教学课程 | `/teach` |
| `./learning-records/*.md` | 学习记录 | `/teach` |

## 常见场景速查

| 场景 | 技能路径 |
|---|---|
| 我刚听说这套 skills，想用 | `/setup-matt-pocock-skills` → `/ask-matt` |
| 我有个新功能想法 | `/grill-with-docs` → `/to-prd` → `/to-issues` |
| 有个设计不确定对不对 | `/prototype` |
| session 快满了，还没讨论完 | `/handoff`，开新 session 继续 |
| 有 bug 要修 | `/diagnosing-bugs` |
| 写新功能想用 TDD | `/tdd` |
| 收到外部 bug 报告 | `/triage` |
| 代码库感觉越来越乱 | `/improve-codebase-architecture` |
| 术语定义有争议 | `/domain-modeling` |
| 想学 TypeScript/某个概念 | `/teach` |
| 我想写个自己的 skill | `/writing-great-skills` |
| 不知道用哪个 skill | `/ask-matt` |
